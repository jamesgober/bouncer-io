# bouncer-io v0.6.0 - Optimisation

**A faster door, measured honestly.** v0.6.0 makes the door 24% faster, the ticket 47% faster, and a bind 70% faster, and fixes two places where inserting bans could slow down without bound. Every number is measured against compositions of existing crates doing the same work on the same data, and published in `docs/PERFORMANCE.md`.

## What is bouncer-io?

<strong>bouncer-io</strong> is the door guy. It refuses banned sources at accept, before a byte is read, and revokes requests that are already running: the next checkpoint a revoked request crosses wipes what it collected, replaces the response with a generic denial, closes the connection, and remembers the offender. A checkpoint costs one atomic load until something is revoked. Rate limiting is one tool inside the door, not its purpose.

## What's in 0.6.0

- **The door**, with 1,000,000 bans: 149 -> 113 ns per admission (`door_at`, pinned to one core). Each prefix's keyed hash is computed once and shared by the ban lookup and the door budgets; nothing is hashed for budgets that are not configured; an empty allow list is skipped.
- **Tickets**: issue and release 85 -> 45 ns. Four fewer atomic read-modify-writes per request cycle; connection ids come from the ticket cell instead of a shared counter.
- **Binds**: about 76 -> 24 ns. The clock is read only when a ban of that kind exists, and shared-address detection uses the door's latest second.
- **Bounded inserts**: offender memory and lift tombstones now evict in constant time. Before, once offender memory was full, each ban insert scanned it, and inserts slowed down without bound (median 3.5 µs at 1.2 million bans; now 457 ns).
- **Checkpoints** stay as cheap as reading a flag (0.2 ns), also while another thread revokes 100,000 times a second (p99 0.8 ns); the slow path with seven keys bound is 64 ns (p99 96 ns).
- **`docs/PERFORMANCE.md`**: the door against the same-job composition (prefix-trie, a hash set, governor, and a revocable handle per connection in a DashMap) and the lookup-only composition, every PLAN 11 target, what changed from 0.5.0, and the method (pinned runs; unpinned results on this CPU swing by 30%).
- **A regression gate**: CI counts instructions on the hot paths with Callgrind; more than 5% over the baseline fails the build.

## Where it stands

Against the same-job composition the door is within 4% for admitted peers and 1.28 times slower for random peers. The target (20% faster) is not met; `dev/ROADMAP.md` lists the remaining steps with their expected gains.
