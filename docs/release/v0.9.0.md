# bouncer-io v0.9.0 - Polish

**The pre-1.0 polish.** Every gap accepted along the way was looked at again, the security and edge-case review was run again in full, and the code was profiled and tuned. The review found real defects, and this release fixes them: a revocation that could miss a running request, concurrency budgets that lost counts, and a grouped ban lookup that had never been switched on. Upgrade from 0.8.0.

## What is bouncer-io?

<strong>bouncer-io</strong> is the door guy. It refuses banned sources at accept, before a byte is read, and revokes requests that are already running: the next checkpoint a revoked request crosses wipes what it collected, replaces the response with a generic denial, closes the connection, and remembers the offender. A checkpoint costs one atomic load until something is revoked. Rate limiting is one tool inside the door, not its purpose.

## Security fixes

- **A revocation could miss a running request.** If another thread moved the revocation epoch at the same moment (a connection closing with live requests, or another bouncer sharing the epoch), `revoke` returned and the ticket kept passing its checkpoints, including `before_commit`. A revocation's birth now comes from the epoch move made after its entry is visible. A new loom model (L-9) fails with the old order.
- **Concurrency budgets lost counts.** A count could land under a key that had just taken its slot over, and nothing returned it. In a test with more keys than slots, every slot of the table ended up holding a stranded count, after which newcomers went uncounted. Key and count now share one word, and a connection returns exactly what it was counted for. Loom models L-6 and L-10 cover the protocol.
- **A client named by a PROXY header could tell a ban from a spent budget**, as a 403 against a 429. Both are now the same denial with the same effect on the ticket.
- **Maintenance could clean up a revocation that a proxied request still owed** while it waited for its client.
- **net-io 0.6.** The `net-io` feature now requires it. net-io 0.5.0 was yanked for a slowloris defect in its reactor.

## Other fixes

- **The grouped ban lookup of 0.8.0 was never switched on.** The 0.8.0 notes described it, but the table was built without it. It is on now, bounded so that one prefix full of bans cannot slow lookups of the addresses inside it or of other prefixes. A random peer's door check is about 7% faster for it, and 13% faster than in 0.8.0 with the rest of this release.
- **Shards shared cache lines.** A ticket at 32 threads took 162 ns; it now takes 58 ns. At 32 threads the door now does 2.9 times the work of the composition it is compared with.
- **Unix-socket and pipe peers were refused** whenever loopback was a trusted proxy. They are now proxy hops, like a TCP peer from loopback.
- **A custom clock under net-io.** The gate judged on net-io's accept time against the bouncer's own clock, so a timed ban could look expired. It now reads the bouncer's clock.
- **A reseed counter race** could panic in debug builds and gave a bogus count in release.

## New

- `DenialCode::http_status` and `DenialCode::from_http_status`. The net-io gate's denial code is now the HTTP status, which serve-net answers with, so a throttle's 429 and an outage's 503 reach the browser as such.
- `docs/READINESS-1.0.md`: what is done, what is open and why, what each open item costs, and the decisions left before 1.0.

## Results

The door against the same-job composition, median of six within-run ratios, one idle core:

| Peers | Against the composition of D-081 | Against the same rate work |
|---|---|---|
| admitted | 16.3% faster | 27.2% faster |
| random | at parity | 15.4% faster |
| random, near the bans | 27.6% faster | 42.2% faster |

The composition of D-081 checks one rate per address. The door checks two, per address and per prefix, so the second column compares the same work. The 20% target against the first is not met; why, and a re-derived target, are in `docs/READINESS-1.0.md` for a decision.

## Fuzzing and soak

Both ran for 24 hours on the final code:

- The five fuzz targets ran 9.5 billion inputs between them (`cidr_parse` 9.1 billion, `delta_decode` 355 million, `snapshot_decode` 30.4 million, `journal_replay` 29.2 million, `directive_sequence` 4.1 million). No crash and no artifact.
- The soak made 8.1 billion connections at about 93,750 a second, refused 540 million of them as banned, and revoked 50.8 million accounts while their requests ran. No revocation was missed. Live heap stayed between 31.914 and 31.923 MB from the first hour to the last.

## Upgrading

- The `net-io` feature needs net-io 0.6, and serve-net 0.6.1 if you use serve-net. The gate must come from the same net-io as the server.
- The net-io gate's denial code is now an HTTP status (403, 429, 503, 404, 401), not 1 to 5. A session of another protocol maps it back with `DenialCode::from_http_status`.
- A client named by a PROXY header that is over its door budget is denied `Forbidden` and its ticket revoked, as when it is banned. It used to get `TooManyRequests`.
- A Unix-socket or pipe peer is a proxy hop when loopback is a trusted proxy.
- A concurrency tier counts at most 1,048,575 live connections per key.
- Account revocation costs about 33 ns more, the price of the revocation fix.
