# bouncer-io v0.12.0 - Classes

**Revocations stop what was running and nothing after it, and budgets can meter a long-lived connection.** A revocation used to refuse its key at the bind of every later ticket until cleanup removed it, so a logout or a password change also refused the account's next requests and WebSocket upgrades. A bind now follows the same rule as a checkpoint. Budget classes are new: a budget the application names and charges once per message, call, or frame, keyed by account. The tests run on serve-net 0.9.

## What is bouncer-io?

<strong>bouncer-io</strong> is the door guy. It refuses banned sources at accept, before a byte is read, and revokes requests that are already running: the next checkpoint a revoked request crosses wipes what it collected, replaces the response with a generic denial, and closes the connection, and a ban keeps the offender out at the door. A checkpoint costs one atomic load until something is revoked. Rate limiting is one tool inside the door, not its purpose.

## Revocations reach only what existed when they were made

A revocation of a session, account, tenant, or fingerprint reaches every ticket that existed when it was made: each one carrying the key is denied at its next checkpoint, and one that binds the key later (a request that arrived before the logout and authenticates after it) is refused at that bind. A ticket issued after the revocation is not reached, so the account's next login, upgrade, or API call binds as usual.

Before 0.12, binds checked every revocation still in the table. Revoking a session or an account therefore acted as a ban on that key for as long as the entry stayed, which depended on when the maintainer ran. Checkpoints had followed the rule above since 0.8.

Keeping a revoked token out of future requests is the session store's job, and a ban's: `Directive::revoke_and_ban(session)` stops what runs and refuses the session from then on.

## Budget classes

```rust
use bouncer_io::{BudgetClass, Budgets, Rate};

const WS_MESSAGES: BudgetClass = BudgetClass(1);
let budgets = Budgets::default().class_rate(WS_MESSAGES, Rate::per_second(50).burst(100));

// For each message on the socket's ticket:
if socket.charge(WS_MESSAGES).is_deny() {
    // over budget: drop this message (or close with 1008)
}
```

- `charge(class)` charges one unit and `charge_n(class, units)` several. Both are made to be called as often as the work happens on a ticket that lives long.
- The key is the ticket's account, else its session, else its client, so all of one account's sockets share one budget.
- Over budget refuses that charge with `TooManyRequests`, and the ticket stays live. A revoked ticket's charge returns its revocation, so the same check ends a socket whose session was revoked.
- Throttles on the ticket's keys multiply the cost. More units than the burst never fit. Allow-listed sources pass.
- When every slot on a key's path holds a key that has not recovered, the charge is refused rather than let through uncounted.
- Up to 64 classes. Refusals are the sampled `bouncer.budget.refused` event.

## Changed

- The tests and `examples/guarded_http.rs` run on serve-net 0.9.0. The `net-io` feature stays on net-io 0.7.2, which serve-net 0.9 also uses.
- Two new tests through serve-net: a connection that never sends a byte closes at its head deadline with no strike, and a head trickled a byte a second is still a slow-peer strike.

## Cost

| Change | Cost |
|---|---|
| Bind rule | None: the bind reads the cell's epoch, a word already in its cache line |
| Budget classes | About 30 ns per charge (estimate: the checkpoint, one keyed probe, one GCRA update); 16 B per key slot per class, 1 MiB per class at the default 65,536 keys; nothing when no class is set |

## Upgrading from 0.11

1. Change the version to `0.12`. Behind serve-net, move to serve-net 0.9; net-io stays 0.7.2.
2. If you relied on `revoke` to refuse a key on new tickets, use `Directive::revoke_and_ban` for that key, or refuse it in your session store.
3. No other code changes. Budget classes are opt-in.
