# bouncer-io v0.9.1 - Shared addresses

**Security fixes for shared addresses, and an example on every public method.** Behind a carrier-grade NAT, an office, or a mobile network, hundreds of people share one address, and bouncer's rule is that nothing short of a deliberate decision bans it. Three routes still could. This release closes them. It also gives every public method its own runnable example and corrects the documentation where it said something other than the code. Upgrade from 0.9.0; the API is unchanged.

## What is bouncer-io?

<strong>bouncer-io</strong> is the door guy. It refuses banned sources at accept, before a byte is read, and revokes requests that are already running: the next checkpoint a revoked request crosses wipes what it collected, replaces the response with a generic denial, closes the connection, and remembers the offender. A checkpoint costs one atomic load until something is revoked. Rate limiting is one tool inside the door, not its purpose.

## Security fixes

All three routes are now refused for a weak word: bouncer's own heuristics, a peer node, or a policy below confidence 70. An administrator, the application, a gate, sentinel, or a confident policy can still ban a shared address by naming it.

- **A directive aimed at a connection or request banned the shared address behind it.** The guard covered only directives aimed at an address. `Directive::ban(request)` from a weak actor took the request's source, so everyone behind the NAT was refused. With the default keys it now bans the ticket's session, as the documentation said. A weak actor that names the source in `ban_keys` gets a throttle, and the receipt says `downgraded`.
- **A decoy touch behind a shared address banned everyone behind it.** A decoy touch is definitive for whoever touched it. Behind a shared address it now bans that session and account, revokes the request, and throttles the address, as a strike threshold does.
- **Another node's automated ban could take an address that is shared here.** A node that saw one client at an address could set a local ban that every peer imported, including peers that see hundreds of people behind it. An imported ban set by another node's local heuristics is now refused (`NotAllowed`, counted in `ImportReport::rejected`) when it covers one client that is shared at the importing node.

Each fix has a test that fails on 0.9.0, with a control showing that a strong actor still bans and that an address nothing is shared behind is banned as before. The cost is one shared-address lookup on each of those paths. All three are cold; the door and the checkpoints are unchanged.

## Documentation

- Every public method has its own runnable example: 181 new, 301 doc tests in all.
- 17 places where `docs/API.md` or the rustdoc disagreed with the code are corrected. The most important: the revocation rate limit applies every revocation and only reports the excess. The table said the excess was observed and not applied.
- CI runs `cargo-semver-checks` against the latest release, so a 0.9.x release that changes the API fails before it ships.

## Upgrading

No API change. What behaves differently:

- `Directive::ban` and `Directive::revoke_and_ban` aimed at a connection or request behind a shared address take the ticket's session instead of the address, unless `ban_keys` names the source and the actor is strong.
- `StrikeKind::DecoyTouched` behind a shared address bans the session and account, not the address.
- `import` refuses a peer's automated ban of a client that is shared at this node.
