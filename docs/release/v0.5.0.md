# bouncer-io v0.5.0 - Feature Complete

**Bans that survive restarts and cross nodes.** v0.5.0 completes the feature set: what one node learns, every node enforces; what a node knew before a restart, it knows after; and the door gets smarter about repeat offenders, provider blocks, and shared addresses.

## What is bouncer-io?

<strong>bouncer-io</strong> is the door guy. It refuses banned sources at accept, before a byte is read, and revokes requests that are already running: the next checkpoint a revoked request crosses wipes what it collected, replaces the response with a generic denial, closes the connection, and remembers the offender. A checkpoint costs one atomic load until something is revoked. Rate limiting is one tool inside the door, not its purpose.

## What's in 0.5.0

- **Persistence.** Bans, lifts, and offender memory survive a restart and are loaded before the first door check. A snapshot plus a journal, CRC32C on every record, an optional keyed BLAKE3 MAC chained across journal batches (nothing can be dropped, reordered, or spliced in without the key), crash-safe snapshot replacement, and a tolerated torn tail. Corrupt or tampered state refuses to start by default. A wall clock stepped between save and load can neither lengthen nor resurrect a ban. `FilePersistence` keeps it in two files; the `Persistence` trait takes any store.
- **Sharing across nodes.** `export_delta`, `export_snapshot`, and `import` carry bans, lifts, offender records, and revocations. Merges converge under any order and repetition (hybrid logical clock stamps, latest end wins, lifts as tombstones). Logging out on one node stops the session's running requests on every node. Channels are rate limited, cannot touch the allow list, cannot lift another node's bans, and cannot pin bans with a clock far in the future.
- **Escalation.** Eight banned addresses in one IPv4 /24, or four /64s in one IPv6 /56 (and four /56s in a /48), ban the parent and fold the children. Never across an allow-list entry, a trusted proxy, or a shared address; never wider than the configured limit.
- **Offender memory.** Past offences decay with a half-life, so a returning offender's next ban is longer and a reformed one is forgotten.
- **Shared addresses.** An address showing many sessions or accounts is treated as a NAT: automation bans the identities and throttles the address instead of punishing everyone behind it.
- **Lane and tenant budgets.** Per-lane rates by session or client, per-tenant token buckets with plans, tenant in-flight limits, and throttles on sessions, accounts, tenants, and fingerprints. A refusal is an ordinary 429 that keeps the connection.
- **Posture.** `set_posture(Strict)` tightens door budgets and switches chosen strike kinds to enforce during a lockdown.
- **Administration.** `explain` says why anything is refused (every covering ban, allow entry, budget and strike state, offender history), `list` pages through bans with filters, `replace_allow` swaps the allow list without making readers wait, and `health` reports loads and the maintainer.
- **Metrics** (feature `metrics`): per-shard counters; the checkpoint fast path stays one load.
- **Datagrams.** `datagram` checks UDP sources; a forged source cannot spend a real client's budget or get it banned.
- **`docs/ARCHITECTURE.md`**: how it is built, what each part costs, and why the concurrent parts are correct.

## Changed

- `Budgets` is no longer `Copy`.
- A merged ban keeps the later issue time; an automated ban already covered by a wider, longer one is not stored.

## What's next

`0.6.0` is optimisation: the door under 100 ns with a million bans, benchmarks against the named competitors, and the table rebuild with a fresh seed.
