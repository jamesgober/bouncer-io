# bouncer-io v0.4.0 - Extended

**Requests already running can be thrown out.** v0.4.0 adds the part of bouncer-io no other gate has: revoke a connection, request, session, account, tenant, source prefix, or fingerprint from any thread, and every running request that carries it is denied at its next checkpoint, its collected response wiped and replaced with a denial, and its connection ejected.

## What is bouncer-io?

<strong>bouncer-io</strong> is the door guy. It refuses banned sources at accept, before a byte is read, and revokes requests that are already running: the next checkpoint a revoked request crosses wipes what it collected, replaces the response with a generic denial, closes the connection, and remembers the offender. A checkpoint costs one atomic load until something is revoked. Rate limiting is one tool inside the door, not its purpose.

## What's in 0.4.0

- **In-flight revocation.** `bouncer.revoke(target, reason)` and `bouncer.apply(directive)`. A checkpoint that begins after `revoke` returned cannot miss it; `before_commit` uses a sequentially consistent load, so a revoked request leaves no side effects. Loom models check the ordering; a stress run of 10^8 checkpoints with concurrent revocations missed none.
- **Identity binds.** `bind_session`, `bind_account`, `bind_tenant`, and `bind_fingerprint` check bans and revocations as the request learns who it is.
- **The transport's check.** Tags (`into_tag`, `Bouncer::request`, `Bouncer::egress`, `Bouncer::release`) let a transport that stores one number per connection check every write, so a pipeline that forgets its checkpoints still cannot send a byte for a revoked connection.
- **Wipe, replace, eject.** `Collected` holds the response and is wiped through crypt-io's volatile writes, never reallocated in place; `deny_and_eject` wipes it, writes the protocol's denial (byte-identical to an ordinary refusal), ejects the connection, and reports.
- **Directives.** Decisions from the security policy, sentinel-sec, the gates, and administrators arrive through one entry. Automated actors never touch allow-listed keys or trusted proxies; a low-confidence ban becomes a throttle.
- **Strikes.** Misbehaviour from any layer is counted in windowed counters. bouncer's own thresholds observe by default and report what they would ban; a decoy touch is definitive.
- **Door budgets.** Rate and concurrency per client (IPv4 address, IPv6 /64) and per prefix, through rate-net's GCRA; trusted proxies and budget-exempt sources are not charged.
- **Events.** Every action goes to the event sink with a stable signal id, so the security signal bridge hears about an attack as bouncer sees it.
- **Maintenance.** Eject-now sweeps, checks on idle tickets (a revoked ticket that never reaches a checkpoint is ejected and reported), and cleanup of revocation entries, from `maintain` or one parked thread that never wakes when nothing is pending.
- **`docs/INTEGRATION.md`**: the checkpoint contract, and how the transport, pipeline, protocol adapter, gates, and signal bridge wire in.

## Changed

- `Bouncer::new` now applies door budgets by default (20 per second, burst 40, and 64 concurrent per client).
- Receipts (`Revocation`, `Applied`, `Lifted`) are no longer `#[must_use]`, so `bouncer.revoke(session, Reason::LOGOUT)?;` reads without warnings.

## What's next

`0.5.0` is feature complete: persistence, sharing bans and revocations across nodes, prefix escalation, offender memory, shared-address detection, lane and tenant budgets, posture, `explain` and `list`, metrics, and health.
